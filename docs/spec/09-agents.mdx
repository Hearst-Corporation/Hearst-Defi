# AI Agents

## Principle

The four structured agents produce **artifacts**, not chat — invisible in UX
except when delivering output. Their contract is unchanged: STRICT JSON,
Zod-validated, no free-form text.

A separate **conversational cockpit chat** also ships — an admin review-mode
facilitator and an LP-facing **Master Agent** — as a deliberately **scoped
exception** to the old "No AI chat" non-negotiable. The in-chat execution path
remains read-only: only a closed-whitelist `navigate` capability + admin
read-tools are callable by the model, and every answer passes the same
compliance guard (forbidden words + APY-range). Admin write tools exist only as
confirmation-gated, explicit human actions (out of the model auto-exec path).
See **ADR-012** and the "Conversational chat" section below.

## The 4 agents

### 1. Scenario Narrative Agent (OpenAI GPT-4.1 — ADR-011)
- **Trigger**: `runScenarioAction()` Server Action (`src/app/(product)/scenario-lab/actions.ts`)
- **Input**: scenario_run JSON (assumptions + computed outputs)
- **Output schema** (`ScenarioNarrativeOutputSchema`, `.strict()`):
  ```ts
  {
    narrative_md: string;       // min 1, max 2000 chars (markdown)
    risk_warning: string;       // min 1, max 500 chars
    confidence: "low" | "medium" | "high";
    key_drivers: string[];      // 1–5 items, each min 1 / max 200 chars
    ptai: {                     // MANDATORY — Projection/Trigger/Action/Impact
      projection: string;       // min 1, max 500 chars
      trigger: string;          // min 1, max 500 chars
      action: string;           // min 1, max 500 chars
      impact: string;           // min 1, max 500 chars
    };
  }
  ```
- **Guardrails**:
  - Forbidden words (6): "guarantee", "promise", "certain", "will deliver", "risk-free", "no risk" — applied to `narrative_md`, `risk_warning`, and all four `ptai` strings
  - `narrative_md` must cite ≥ 1 engine assumption
  - If confidence = low → `narrative_md` must say "low confidence" explicitly (enforced)
  - `ptai` is required (non-negotiable #3); the UI `<Ptai>` primitive and the Investor Memo PDF render it without re-parsing the prose

### 2. Mining Health Agent (OpenAI GPT-4.1 — ADR-011)
- **Trigger**: daily 08:00 UTC cron + on-demand from Dashboard
- **Input**: 30d hashprice, difficulty change, margin, uptime, period
- **Output schema** (`MiningHealthOutputSchema`, `.strict()`):
  ```ts
  {
    alert_level: "green" | "amber" | "red";
    summary: string;            // min 1, max 1000 chars
    recommendation: string;     // min 1, max 500 chars (suggests, never executes)
  }
  ```
- **Guardrails**:
  - Red alert → notify manager (no auto-action)
  - Alert rubric applied consistently — red: margin < 5 OR uptime < 95 OR difficulty change > 10; amber: margin < 15 OR uptime < 97 OR difficulty change > 5; green otherwise
  - `summary` must cite ≥ 1 assumption (enforced) and ≥ 1 numeric metric

### 3. Risk Explanation Agent (OpenAI GPT-4.1 — ADR-011)
- **Trigger**: daily + on every rebalancing event
- **Input**: 5 risk scores + 30d evolution + current allocation
- **Output schema** (`RiskExplanationOutputSchema`, `.strict()`):
  ```ts
  {
    top_risks: Array<{                                    // 1–2 items
      risk_id: "market" | "mining" | "liquidity" | "smart_contract" | "counterparty";
      name: string;               // min 1
      explanation: string;        // min 1
      suggested_guardrail: string; // min 1
    }>;
    overall_summary: string;      // min 1
  }
  ```
- **Guardrails**:
  - Guardrails proposed must stay within vault bounds
  - Never claims "we will fix" — proposes, doesn't decide

### 4. Investor Memo Agent (OpenAI GPT-4.1 — ADR-011, max_tokens 4096)
- **Trigger**: click "Generate memo" — bound to a vault id (ADR-006 #9)
- **Input**: vault state + scenarios + backtests + methodology version
- **Output schema** (`InvestorMemoOutputSchema`, `.strict()` — flat 8-field Markdown):
  ```ts
  {
    executive_summary: string;    // min 1, markdown
    vault_structure: string;      // min 1, markdown
    scenario_analysis: string;    // min 1, markdown
    risk_section: string;         // min 1, markdown (5 canonical risks)
    mining_section: string;       // min 1, markdown
    performance_section: string;  // min 1, markdown
    methodology_note: string;     // min 1, markdown
    disclaimer: string;           // min 1, verbatim template
  }
  ```
- **Guardrails**:
  - Methodology + disclaimers injected as immutable system blocks. `cache_control: "ephemeral"` is accepted but ignored by the wrapper; OpenAI applies automatic prompt caching for prompts > 1024 tokens (ADR-011)
  - Disclaimers NEVER generated, only templated; reproduced verbatim in `disclaimer`
  - All 7 narrative sections must cite ≥ 1 assumption (enforced); `disclaimer` is exempted (verbatim legal text)
  - APY is always a range; if data missing → stated explicitly in the relevant section, no invention

## Stack

- **OpenAI GPT-4.1** — single model for all 4 agents **and** the cockpit chat (ADR-011, 2026-06-11, supersedes ADR-007 / Kimi-via-Hypercli, retired)
- `openai@6.x` SDK from `OPENAI_API_KEY` (optional `OPENAI_BASE_URL`, `OPENAI_ORG_ID`); model id `OPENAI_MODEL` (default `gpt-4.1`). The historical client export `kimi` / `KIMI_MODEL` are legacy aliases that now resolve to OpenAI (no Kimi, no Anthropic SDK in this codebase)
- `cache_control: "ephemeral"` is accepted but ignored by the wrapper; OpenAI applies **automatic prompt caching** for prompts > 1024 tokens, so the re-sent methodology block is partially cached at no code cost
- All outputs validated via Zod `.strict()` schemas (`src/lib/agents/schemas.ts`)
- Forbidden-words list is canonical in `src/lib/agents/forbidden-words.ts`; the agent guard (`assertNoForbiddenWords`, `assertCitesAssumption`) lives in `src/lib/agents/validators.ts`
- Cost/usage tracked in `LlmRun` Prisma table (GPT-4.1 list pricing $2.00 / $8.00 per MTOK, computed in `client.ts`)
- Admin tool telemetry (`agentName = "admin-chat-tool"`) is also persisted in `LlmRun`: `model=<chatMode>:<profile>`, `promptHash=<toolId>`, status `success|blocked|failed|confirmation_required`, and bounded `errorMessage` (max 500 chars)

## Conversational chat (scoped exception — ADR-012)

A conversational cockpit chat ships **alongside** the four structured agents, on
the same model (GPT-4.1). It is a **read-only** assistant — it explains the
product and can guide the user to a page, but it cannot transact, write, or take
any admin action. Three admin-selectable modes:

- **Admin review-mode facilitator** — admin-gated (`AdminChatMode` row → `chatMode = "review"`); a product-review facilitator prompt that produces review documents (MD + JSON). Always runs through the `@hearst/cockpit-shell` handler (no tools).
- **Admin ops mode** — admin-gated (`chatMode = "admin"`); internal copilot prompt for architecture, canonical allocations, market-data freshness, proofs, governance, deployment runbooks and operational checks. It can use injected app context but has no browser, market terminal, DB-write, signing, Fireblocks, deploy or transaction tool.
  - Internal implementation: the admin live block is assembled through a typed tools registry (`src/lib/llm/tools/*`) with explicit policy gating (`chatMode/profile`). Current runtime context enrichment uses read-tools (`read_allocations_canonical`, `read_market_snapshot`, `read_routes_index`, `read_specs_index`, `read_runtime_capabilities`); partial backend failures degrade gracefully (best-effort context).
  - Admin read utilities also include deterministic planning/spec tools: `generate_chart_spec` (structured chart spec with provenance/freshness and explicit unavailable flags), `generate_demo_plan` (ordered route-based demo steps constrained by admin whitelist + route/spec indexes), `export_demo_pack` (structured export: metadata + ordered demo plan + optional chart specs + optional checklist + provenance/freshness summary), and `export_briefing_pack` (executive-ready package: summary + ordered demo plan + optional chart specs + risk/action sections + provenance/freshness summary).
  - In-chat tool-calling is enabled only in `admin` mode for a bounded server allowlist of **read** tools from the same registry; tool outputs are fed back into the same model turn (controlled two-pass flow).
  - `POST /api/admin/chat-tools` supports `execute_read` with optional `input` JSON for these read-only tools; no write side effect is permitted in this path.
  - **Read payload redaction contract**: tool outputs are deterministic, schema-bounded and read-only (`multiline_text_block` or typed `json_object`), with no secrets/env vars/internal IDs leakage. Missing data is returned as explicit `unavailable` markers instead of raw backend errors.
  - Any attempted model-side auto-execution of a write tool is deterministically blocked server-side (non-sensitive warning log), with no side effects; write remains explicit human confirmation flow only.
  - Admin write-tools for **draft-only** actions (`create_review_note_draft`, `create_governance_proposal_draft`) are exposed through `GET/POST /api/admin/chat-tools` (admin-only). They are **not auto-triggered by LLM output**: execution is explicit from the admin controls panel ("Actions admin"), and always uses a two-step handshake: step 1 returns `confirmation_required` (token + summary), step 2 requires explicit confirm click + token. Tokens are short-TTL and single-use; expired/invalid tokens are rejected server-side.
  - **Confirmation token binding contract**: token is user-bound and tied to `(userId, toolId, payloadHash)` where payload hash is computed from a canonicalized input payload. Any user/tool/payload mismatch, replay (`usedAt`) or expiry rejects execution.
- **LP-facing Master Agent** — normal-mode chat, flag-gated behind `CHAT_MASTER_AGENT` (server-only env, OFF by default). Runs through the app-owned tool-capable engine (`runChatAgent`) whose **only** tool is `navigate` — a client-side, read-only route change restricted to a **closed whitelist** (`NAV_DESTINATIONS`: portfolio, vaults, proof-center, profile). No write / financial / admin tool exists.

Guardrails (all enforced server-side):

- **System prompt is server-built** (`COCKPIT_DEFAULT_SYSTEM_PROMPT` + role directive). A client `system` field is stripped by the inbound Zod schema — it cannot override the curated prompt.
- **Output-side compliance guard** (`guardChatStream` / `chatOutputViolation`) wraps the streamed answer and enforces the **same** forbidden-words list (FR ∪ EN, negation-aware) plus the **APY-always-a-range** rule, aborting before any offending span is emitted. Navigation fires only on a compliant answer.
- **Role-aware register** (`buildRoleDirective`): LP default is strict vouvoiement + zero internal disclosure; admin gets a looser internal register but still no secrets / env vars / DB schemas / other agents' prompts.
- **No vector RAG today**: chat context is server-built from Prisma-backed user profile/memory, live portfolio context when available, static prompts, and filesystem route/spec indexes for review document generation.
- **Human-in-the-loop preserved** (#4): no auto-execution of any financial or rebalancing action — the chat suggests and navigates, humans decide.
- **Write confirmation binding**: confirmation tokens are short-TTL, single-use, and bound to `(userId,toolId,payloadHash)`; replay or payload mismatch is rejected server-side.

## Forbidden absolutely

- ❌ Free-form chat from the **structured agents** (they return STRICT JSON only)
- ❌ Any autonomous write / financial execution by conversational chat (write tools are explicit confirm-only, never model auto-exec)
- ❌ Unsourced recommendations
- ❌ Yield affirmations / guarantees
- ❌ Autonomous decisions (agents propose, humans decide)
