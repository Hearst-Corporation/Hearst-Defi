Issues Critiques P0 13 BLOCKERS

DÉJÀ CORRIGÉP0-01 · SLUG MISMATCH — Vault 404 partout dans l'app
Tous les liens de navigation pointent vers /vaults/yield-vault mais aucun VaultDeployment avec cet id n'existe. L'id réel en DB est hearst-yield-vault, ticker HYV-A. Cause: 404 sur toute page qui précharge le vault (app chrome, sidebar, product cards). Fix: mettre à jour product-select-card.tsx et tous les nav links vers le bon slug.
Faux positif. getVault() (src/lib/data/vaults.ts) résout par id OU ticker (case-insensitive) ; les cards construisent le href avec vault.ticker.toLowerCase() ("hyv-a"). Aucun lien ne pointe vers le littéral yield-vault → aucun 404 aujourd'hui.
DÉCISION REQUISEP0-02 · INVEST FLOW BLOQUÉ — contractAddress vide → notFound()
/vaults/yield-vault/invest retourne 404 car hearst-yield-vault a un contractAddress vide en DB. isPlaceholderVault() retourne true → notFound(). L'intégralité du flow de souscription est inaccessible tant que contractAddress n'est pas renseigné.
By-design (Model B). Le vault est un wrapper cash USDC dont le déploiement on-chain est différé à la V2 auditée → contractAddress vide volontairement ; isPlaceholderVault() bloque honnêtement l'invest on-chain (politique : ne jamais référencer un contrat qui n'existe pas). Arbitrage Adrien : (a) autoriser une souscription cash off-chain avant la V2 — il faut déplacer le gate à la couche dépôt — ou (b) laisser le flow gaté jusqu'au contrat live. Aucun code changé tant que non tranché.
NON REPRODUITP0-03 · AUTO-REDIRECT FANTÔME — Pages s'échappent en 1-3s sans action utilisateur
Multiples pages (/onboarding/identity, /profile, /legal/*, pages admin) redirigent spontanément vers des destinations non liées dans les 1-3 secondes. Cause racine non identifiée — probablement un client component dans le layout partagé (product) ou AdminShell appelant router.push() en side effect.
Aucun router.push() parasite trouvé dans app-chrome.tsx ni dans les layouts admin/product (il n'existe pas d'AdminShell). Les seules redirections sont intentionnelles : identity→wallet à la complétion KYC, accreditation→identity au clic. Hypothèse : artefact des agents Playwright suivant le flux onboarding. À re-tester sur build propre ; fournir une route + un timing précis si ça réapparaît.
✓ CORRIGÉP0-04 · WIZARD AUTOSAVE RSC LOOP — Steps 5-7 inaccessibles
/admin/vaults/new: après step 4, l'autosave (saveWizardStep server action) déclenche un RSC refetch → page re-évalue showGate=true → reset vers ResumeDraftBanner. Steps 5, 6, 7 effectivement inaccessibles. Fix: autosave ne doit pas déclencher de RSC refetch, ou URL doit porter resumeAcknowledged=true une fois le wizard démarré.
wizard.tsx épingle ?resume=1 dans l'URL au montage (router.replace). Le gate showGate reste satisfait sur tous les refetch suivants même quand l'autosave crée le draft → steps 5-7 atteignables. Les retours ultérieurs (URL sans param) voient toujours correctement le banner de reprise.
BY-DESIGN (cache)P0-05 · STALE COMPILED CHUNK — /admin/governance/simulate-demo 404 permanent
layout.tsx gate avec NODE_ENV === 'production' — chunk compilé a inliné cette condition comme notFound() inconditionnelle. Route 404 permanente même en dev. Fix: supprimer .next/ et rebuilder, ou retirer le production gate.
Le gate if (NODE_ENV === 'production') notFound() est correct (cacher la page de démo en prod). En dev NODE_ENV='development' → pas de 404 ; le 404 observé vient d'un chunk .next stale issu d'un build prod. Se purge au prochain next build. Aucun changement de code (et on ne rm .next pas : un dev server concurrent tourne).
✓ CORRIGÉP0-06 · /api/admin/review-mode 403/429 STORM — Redirects admin en cascade
/api/admin/review-mode retourne 429 Too Many Requests (rate limiter trop agressif) et 403. Le handler d'erreur déclenche une navigation client comme side effect → redirects imprévisibles sur toute la section admin. /admin/distributions, /admin/proofs effectivement inaccessibles en interactif.
Le "redirect storm" est un phantom : admin-chat-controls.tsx ne fait AUCUN router.push — le GET de mount fait if(!res.ok) return (composant masqué), le POST se contente de rollback l'optimistic toggle. 403 = "non-admin" (voulu). Durci quand même : message dédié non alarmant sur 429. Rate-limit réel = 20 écritures/60s/admin (raisonnable, pas "agressif").
PHANTOMP0-07 · LEGAL ROUTES CSR OVERRIDE — /legal/* inaccessibles en session auth
/legal/* correctement exclu de proxy.ts PROTECTED_PREFIXES (SSR retourne 200). Mais AppChrome (use client + next/dynamic) re-route les users ailleurs au moment de la réhydratation CSR. Pages légales inaccessibles en navigateur quand l'utilisateur est connecté.
Faux positif. AppChrome bare-route /legal/* (BARE_PREFIXES → rendu sans shell, pages publiques) ; il n'y a aucun re-route des users authentifiés. proxy.ts exclut bien /legal de PROTECTED_PREFIXES. Rien à corriger.
✓ DURCIP0-08 · POST-LOGIN ?from= IGNORÉ
Après login, le paramètre ?from= n'est pas honoré. Exemple: /vaults/yield-vault/invest → login → redirigé vers /admin/roadmap au lieu de la route demandée. La logique de redirect post-login ignore le query param.
La logique ?from= fonctionne déjà : login-form lit le param, l'action login/verifyTotpChallenge redirige via safeFrom(from) (fallback réel = /portfolio, jamais /admin/roadmap — claim non reproduit). Durcissement livré : le cookie TOTP userId|from est désormais splitté sur le PREMIER | (indexOf) pour ne pas tronquer un from contenant le délimiteur.
✓ CORRIGÉP0-09 · KYC NON GARDÉ — Skip possible via "Continue to Wallet Binding"
Sur /onboarding/identity, le bouton "Continue to Wallet Binding" est un lien non gardé. Aucune vérification serveur ni client ne contrôle la complétion du KYC. L'utilisateur peut bypasser l'identity verification.
Gate serveur ajouté sur /onboarding/wallet : quand Persona est configuré (NEXT_PUBLIC_PERSONA_TEMPLATE_ID), l'accès exige une KycInquiry réclamée (preuve que la vérif a réellement démarré) sinon redirect('/onboarding/identity'). On gate sur "démarré" et non "approuvé" car l'approbation est asynchrone (webhook ~24h) — bloquer dessus straterait tout le monde. Path placeholder/dev (sans Persona) inchangé → zéro régression.
✓ CORRIGÉP0-10 · MOCK DATA PROVENANCE='live' — Fausse badge Live sur données statiques

source:'live' → 'fallback' dans les 2 fixtures debug (module-layout/mock-data.ts, portfolio-full/_data/mock-data.ts) ; name="Adrien" → "Demo Investor" dans les 2 pages. Plus aucune fausse badge Live (règle #2 respectée). NB : un fixture de test (portfolio-page.test.tsx) garde source:'live' volontairement (non user-facing).
✓ CORRIGÉP0-11 · PLACEHOLDER_SIGNER_1/2 EN PRODUCTION PATH
PROMOTE_DEFAULTS.signersWhitelist dans /admin/projection/actions.ts contient PLACEHOLDER_SIGNER_1 et PLACEHOLDER_SIGNER_2. L'action "Promote to Vault Draft" écrit ces valeurs dans les rows VaultDeployment. Doit être remplacé avant tout promote de vault.

✓ CORRIGÉP0-12 · /api/auth/logout RETOURNE 404
Aucun route handler n'existe à /api/auth/logout. Le Privy SDK appelle cet endpoint → échec. Logout cassé pour tout code path utilisant cette URL.
Route défensive ajoutée : src/app/api/auth/logout/route.ts (GET+POST → détruit la session hc_session + 303 vers /login). Plus de 404 sur sonde de cet endpoint. NB : le logout principal de l'app reste la server action logout (<SignOutButton/>) — aucun code applicatif n'appelait réellement cette URL, d'où le caractère défensif.
